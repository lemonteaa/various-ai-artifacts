## 1. The core mental model

In Crossplane v2-style land, separate these four ideas:

1. **XRD**  
   Defines a new API.  
   In your case: a namespaced claim kind `App`, backed by a composite kind `XApp`.

2. **Claim**  
   What a user/team applies.  
   Example: `App` in namespace `team-a`.

3. **Composition**  
   Says: “When an `XApp` exists, run this pipeline of functions to produce desired resources.”

4. **Composition Functions**  
   The actual implementation logic.  
   In v2, the blessed path is **not** “Composition contains a built-in templating language”.  
   It is:

   ```text
   Composition -> pipeline of Functions -> desired managed resources
   ```

The old v1 built-in patch-and-transform mini-language is effectively replaced by a function: usually `function-patch-and-transform` for the classic low-code style, or another function such as Go templating, KCL, or a custom Go function.

So the v2 answer to “low-code is not enough” is not exactly “everyone must write Go”. It is:

> The composition engine is a function pipeline.  
> Use existing functions when possible.  
> Write a custom function when you need real logic.

For your `App = Deployment + Service` case, you usually **do not need a custom Go function**. The classic patch-and-transform function is enough, and it is the clearest example.

## 2. Scenario

You want:

- A control-plane cluster running Crossplane.
- A target Kubernetes cluster:
  - either a different cluster,
  - or the same cluster but a different namespace.
- A claim called `App`.
- The claim creates:
  - a `Deployment`
  - a `Service`

in the target cluster/namespace.

Crossplane does not directly create `Deployment` objects as core Crossplane resources. It needs a provider. For arbitrary Kubernetes objects, the normal provider is:

```text
provider-kubernetes
```

It exposes a managed resource called `Object`, which wraps an arbitrary Kubernetes manifest.

So the actual composed resources will look like:

```text
App claim
  -> XApp composite
    -> provider-kubernetes Object: Deployment
    -> provider-kubernetes Object: Service
      -> real Deployment + Service in target cluster
```

## 4. Give Crossplane access to the target cluster

### Remote target cluster

Create a kubeconfig secret readable by the Kubernetes provider.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: target-cluster-kubeconfig
  namespace: crossplane-system
type: Opaque
stringData:
  kubeconfig: |
    apiVersion: v1
    kind: Config
    clusters:
    - name: target-cluster
      cluster:
        server: https://target-cluster.example.com:6443
        certificate-authority-data: <base64-ca>
    contexts:
    - name: target-cluster
      context:
        cluster: target-cluster
        user: target-cluster-user
    current-context: target-cluster
    users:
    - name: target-cluster-user
      user:
        token: <token>
```

Then create a `ProviderConfig`:

```yaml
apiVersion: kubernetes.crossplane.io/v1alpha1
kind: ProviderConfig
metadata:
  name: target-cluster
spec:
  credentials:
    source: Secret
    secretRef:
      namespace: crossplane-system
      name: target-cluster-kubeconfig
      key: kubeconfig
```

### Same cluster, different namespace

If the target is the same cluster as the Crossplane control plane, you still usually use `provider-kubernetes`. You can either:

- create a `ProviderConfig` that uses in-cluster/injected credentials, or
- rely on a default provider config if your setup has one.

The important conceptual point:

> The claim namespace is not automatically the workload namespace.  
> You must explicitly decide where the Deployment/Service should go.

In the example below, we use an explicit `targetNamespace` parameter.

## 5. Define the `App` API with an XRD

This creates:

- a namespaced claim kind: `App`
- a cluster-scoped composite kind: `XApp`

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: xapps.example.org
spec:
  group: example.org
  names:
    kind: XApp
    plural: xapps
  claimNames:
    kind: App
    plural: apps
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                parameters:
                  type: object
                  properties:
                    targetNamespace:
                      type: string
                    image:
                      type: string
                    replicas:
                      type: integer
                      minimum: 0
                    containerPort:
                      type: integer
                  required:
                    - targetNamespace
                    - image
                    - replicas
                    - containerPort
              required:
                - parameters
```

After applying this, you should see new API resources:

```bash
kubectl api-resources | grep example.org
```

Expected:

```text
apps     App     namespaced
xapps    XApp    cluster-scoped
```

## 6. The v2-style Composition

This is the important part.

This Composition does **not** use old built-in `spec.resources` patch-and-transform directly. It uses a function pipeline:

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: xapps.example.org
spec:
  compositeTypeRef:
    apiVersion: example.org/v1alpha1
    kind: XApp

  # Some Crossplane versions still accept/expect this.
  # If your v2 CRD rejects it, remove this line.
  # In v2-style land, pipeline is the actual execution model.
  mode: Pipeline

  pipeline:
    - step: render-app-objects
      functionRef:
        name: function-patch-and-transform
      input:
        apiVersion: pt.fn.crossplane.io/v1beta1
        kind: Resources
        resources:
          - name: deployment
            base:
              apiVersion: kubernetes.crossplane.io/v1alpha2
              kind: Object
              metadata:
                generateName: app-deploy-
              spec:
                providerConfigRef:
                  name: target-cluster
                forProvider:
                  manifest:
                    apiVersion: apps/v1
                    kind: Deployment
                    metadata:
                      name: placeholder
                      namespace: placeholder
                      labels: {}
                    spec:
                      replicas: 1
                      selector:
                        matchLabels: {}
                      template:
                        metadata:
                          labels: {}
                        spec:
                          containers:
                            - name: app
                              image: placeholder
                              ports:
                                - containerPort: 8080
            patches:
              - fromFieldPath: metadata.name
                toFieldPath: spec.forProvider.manifest.metadata.name
                transforms:
                  - type: string
                    string:
                      type: Format
                      fmt: "%s-deploy"

              - fromFieldPath: spec.parameters.targetNamespace
                toFieldPath: spec.forProvider.manifest.metadata.namespace

              - fromFieldPath: metadata.name
                toFieldPath: spec.forProvider.manifest.metadata.labels[app]

              - fromFieldPath: metadata.name
                toFieldPath: spec.forProvider.manifest.spec.selector.matchLabels[app]

              - fromFieldPath: metadata.name
                toFieldPath: spec.forProvider.manifest.spec.template.metadata.labels[app]

              - fromFieldPath: spec.parameters.image
                toFieldPath: spec.forProvider.manifest.spec.template.spec.containers[0].image

              - fromFieldPath: spec.parameters.replicas
                toFieldPath: spec.forProvider.manifest.spec.replicas

              - fromFieldPath: spec.parameters.containerPort
                toFieldPath: spec.forProvider.manifest.spec.template.spec.containers[0].ports[0].containerPort

          - name: service
            base:
              apiVersion: kubernetes.crossplane.io/v1alpha2
              kind: Object
              metadata:
                generateName: app-svc-
              spec:
                providerConfigRef:
                  name: target-cluster
                forProvider:
                  manifest:
                    apiVersion: v1
                    kind: Service
                    metadata:
                      name: placeholder
                      namespace: placeholder
                      labels: {}
                    spec:
                      type: ClusterIP
                      selector: {}
                      ports:
                        - name: http
                          port: 80
                          targetPort: 8080
            patches:
              - fromFieldPath: metadata.name
                toFieldPath: spec.forProvider.manifest.metadata.name
                transforms:
                  - type: string
                    string:
                      type: Format
                      fmt: "%s-svc"

              - fromFieldPath: spec.parameters.targetNamespace
                toFieldPath: spec.forProvider.manifest.metadata.namespace

              - fromFieldPath: metadata.name
                toFieldPath: spec.forProvider.manifest.metadata.labels[app]

              - fromFieldPath: metadata.name
                toFieldPath: spec.forProvider.manifest.spec.selector[app]

              - fromFieldPath: spec.parameters.containerPort
                toFieldPath: spec.forProvider.manifest.spec.ports[0].targetPort

    - step: automatically-ready
      functionRef:
        name: function-auto-ready
```

### What is happening here?

The `function-patch-and-transform` function receives the observed `XApp`, then produces two desired managed resources:

```text
kubernetes.crossplane.io/Object for Deployment
kubernetes.crossplane.io/Object for Service
```

Those `Object` resources are managed by `provider-kubernetes`, which applies the actual Kubernetes manifests to the target cluster selected by:

```yaml
providerConfigRef:
  name: target-cluster
```

The `function-auto-ready` function then helps mark the composite resource ready when the composed resources are ready.

## 7. Create an `App` claim

This is what a normal user/team applies.

```yaml
apiVersion: example.org/v1alpha1
kind: App
metadata:
  name: web
  namespace: team-a
spec:
  compositionRef:
    name: xapps.example.org
  parameters:
    targetNamespace: team-a-apps
    image: nginx:1.27
    replicas: 2
    containerPort: 8080
```

Apply it:

```bash
kubectl apply -f app-claim.yaml
```

Then inspect:

```bash
kubectl get app web -n team-a
kubectl get xapps
kubectl get objects.kubernetes.crossplane.io
```

```bash
kubectl --context=target-cluster -n team-a-apps get deployment,service
```

You should see something like:

```text
deployment.apps/<xr-name>-deploy
service/<xr-name>-svc
```

where `<xr-name>` is the generated `XApp` composite resource name.

## 8. Important namespace details

A common source of confusion:

```text
Claim namespace != workload target namespace
```

Your claim lives here:

```yaml
metadata:
  namespace: team-a
```

But the Deployment/Service are created where you tell them to:

```yaml
parameters:
  targetNamespace: team-a-apps
```

If you want the workload namespace to follow the claim namespace, you can patch from the claim ref instead.

For example, replace:

```yaml
- fromFieldPath: spec.parameters.targetNamespace
  toFieldPath: spec.forProvider.manifest.metadata.namespace
```

with:

```yaml
- fromFieldPath: spec.claimRef.namespace
  toFieldPath: spec.forProvider.manifest.metadata.namespace
```

But be careful with remote clusters: the claim namespace may not exist in the target cluster.

## 9. If you want multiple target clusters

The example hardcodes:

```yaml
providerConfigRef:
  name: target-cluster
```

For a real multi-cluster PaaS, you usually parameterize this.

Add to the XRD:

```yaml
providerConfigName:
  type: string
```

Then in the Composition, patch both `Object` resources:

```yaml
- fromFieldPath: spec.parameters.providerConfigName
  toFieldPath: spec.providerConfigRef.name
  policy:
    fromFieldPath: Optional
```

Then users can do:

```yaml
spec:
  parameters:
    providerConfigName: prod-cluster
    targetNamespace: team-a-apps
    image: nginx:1.27
    replicas: 2
    containerPort: 8080
```

This is one of Crossplane’s genuinely useful abstractions: the claim API can stay stable while the actual target cluster is selected by a `ProviderConfig`.

## 10. If the target namespace does not exist

The example assumes `team-a-apps` already exists in the target cluster.

If you want Crossplane to create it too, you can add a third `Object` resource:

```yaml
- name: namespace
  base:
    apiVersion: kubernetes.crossplane.io/v1alpha2
    kind: Object
    metadata:
      generateName: app-namespace-
    spec:
      providerConfigRef:
        name: target-cluster
      forProvider:
        manifest:
          apiVersion: v1
          kind: Namespace
          metadata:
            name: placeholder
  patches:
    - fromFieldPath: spec.parameters.targetNamespace
      toFieldPath: spec.forProvider.manifest.metadata.name
```

For strict ordering, especially if you have many dependent resources, you may want to add `function-sequencer`. For a simple Deployment/Service example, Crossplane/provider retries often tolerate eventual consistency, but for production you should think about ordering explicitly.

## 11. Where the “v2 controversy” lands

Your read is basically correct:

> The original built-in patch-and-transform mini-language was too weak for real-world compositions.

Crossplane’s answer in v2-style architecture is:

> Make the composition engine function-based.

That has advantages:

- You can keep low-code style with `function-patch-and-transform`.
- You can use templating functions like Go templating or KCL.
- You can write custom functions for real logic.
- You can mix and compose functions.
- The XR/claim/provider machinery stays standardized.

But it also exposes the uncomfortable question:

> If I end up writing a lot of Go anyway, why not just write an operator?

That is a fair question.

The honest answer is:

### Use Crossplane when you want these things

- Self-service claim APIs.
- XRD-defined abstraction boundaries.
- Composition of multiple providers:
  - Kubernetes
  - Helm
  - cloud APIs
  - databases
  - DNS
  - IAM
  - secrets
- A standardized desired-state model.
- Provider ecosystem.
- Policy/integration points around claims and compositions.
- Multi-environment/multi-cluster provider configs.

### Use a custom operator when

- Your domain is mostly Kubernetes-native workload logic.
- You need complex day-2 operations.
- You need deeply custom status/state machines.
- You need custom controllers watching arbitrary resources.
- Crossplane’s provider/function model is just adding indirection.
- Your team already has strong operator-sdk/controller-runtime patterns.

If your “PaaS” is only:

```text
Deployment + Service + Ingress + ConfigMap
```

then Helm/Kustomize/Argo CD or a custom operator may be simpler than Crossplane.

Crossplane becomes much more compelling when `App` means:

```text
Deployment
+ Service
+ Ingress
+ Database
+ DNS record
+ IAM role
+ secret/connection details
+ policy constraints
+ provider-specific lifecycle
```

That is where the composition abstraction earns its keep.

## 12. If you did write a custom Go function

You would package a function as a Crossplane `Function`, then call it from the pipeline.

Conceptually, using the Go function SDK, it looks like this:

```go
// Pseudocode; exact import paths vary by function-sdk-go version.

type Function struct {
    function.UnimplementedRunner
}

func (f *Function) RunFunction(
    ctx context.Context,
    req *fn.RunFunctionRequest,
) (*fn.RunFunctionResponse, error) {
    rsp := response.ToRunFunctionResponse(req)

    // Read the observed composite resource.
    xr := resource.GetObservedCompositeResource(req)

    // Extract spec.parameters from xr.
    // Build desired provider-kubernetes Object resources.

    // deploy := &unstructured.Unstructured{...}
    // svc := &unstructured.Unstructured{...}

    response.SetDesiredComposedResource(rsp, "deployment", deploy)
    response.SetDesiredComposedResource(rsp, "service", svc)

    return rsp, nil
}
```

Then your Composition becomes:

```yaml
spec:
  compositeTypeRef:
    apiVersion: example.org/v1alpha1
    kind: XApp
  mode: Pipeline
  pipeline:
    - step: render-app
      functionRef:
        name: function-my-app
```

The important distinction:

> A Crossplane function is not a full controller.  
> It is usually a stateless transformation invoked by Crossplane during reconciliation.

Crossplane still handles:

- claim lifecycle
- XR lifecycle
- composition selection
- invoking functions
- applying desired managed resources
- status aggregation
- retries/reconciliation
- provider wiring

A custom operator gives you more direct control, but you own all of that machinery yourself.

## 13. Practical debugging tips

Check packages:

```bash
kubectl get providers
kubectl get functions
```

Check claims:

```bash
kubectl get apps -A
kubectl describe app web -n team-a
```

Check composites:

```bash
kubectl get xapps
kubectl describe xapp <xr-name>
```

Check composed managed resources:

```bash
kubectl get objects.kubernetes.crossplane.io
kubectl describe object.kubernetes.crossplane.io <object-name>
```

Check target cluster:

```bash
kubectl --context=target-cluster -n team-a-apps get all
```

Common failure modes:

1. **Function not installed or not healthy**

   ```bash
   kubectl get functions
   ```

2. **Provider not installed or not healthy**

   ```bash
   kubectl get providers
   ```

3. **ProviderConfig missing or wrong secret**

   ```bash
   kubectl describe providerconfig target-cluster
   ```

4. **Target namespace missing**

   The Deployment/Service object creation may fail until the namespace exists.

5. **RBAC on target cluster too weak**

   The kubeconfig/token used by `provider-kubernetes` must be allowed to create Deployments and Services in the target namespace.

6. **Composition still using old v1 built-in P&T style**

   In v2-style compositions, prefer:

   ```yaml
   spec:
     pipeline:
       - step: ...
         functionRef:
           name: ...
   ```

   over old:

   ```yaml
   spec:
     resources:
       - base: ...
   ```

## 15. Short version

For your exact scenario, the v2-blessed shape is:

```text
XRD: App claim -> XApp composite
Composition: pipeline of functions
function-patch-and-transform: renders provider-kubernetes Objects
provider-kubernetes: applies Deployment + Service to target cluster
function-auto-ready: marks XR ready
```

The minimal production-like flow is:

```text
Install functions
Install provider-kubernetes
Create ProviderConfig for target cluster
Create XRD
Create Composition with function pipeline
Apply App claim
```

And the key philosophical takeaway:

> Crossplane v2 does not necessarily force you to write Go for every composition.  
> It forces composition logic to live in functions.  
> Low-code can still exist as a function.  
> Custom code can also be a function.  
> If your custom code becomes large and Kubernetes-only, then yes, comparing it directly to a custom operator is absolutely the right discussion.

### ASSISTANT
For a single-cluster lab, the approach is simpler but conceptually identical: you create a dedicated ServiceAccount with scoped-down permissions, generate a kubeconfig that points back to the same API server using that SA's token, and wire it into a `ProviderConfig`.

Here are the exact YAMLs in the order you should apply them.

## 1. Create the target workload namespace

This is where your Deployment/Service will actually live.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-apps
```

## 2. Create a dedicated ServiceAccount for the provider

This SA will be used by `provider-kubernetes` when it talks to the API server to create your workloads.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: provider-kubernetes-target
  namespace: crossplane-system
```

## 3. Create a long-lived token Secret for that SA

In Kubernetes 1.24+, service account tokens are not auto-created. You need to explicitly create one.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: provider-kubernetes-target-token
  namespace: crossplane-system
  annotations:
    kubernetes.io/service-account.name: provider-kubernetes-target
type: kubernetes.io/service-account-token
```

Wait a few seconds for the token controller to populate it:

```bash
kubectl wait --for=jsonpath='{.data.token}' secret/provider-kubernetes-target-token -n crossplane-system --timeout=30s
```

## 4. Create scoped RBAC in the target namespace

This gives the SA permission to manage Deployments and Services **only** in `team-a-apps`.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: provider-kubernetes-target-role
  namespace: team-a-apps
rules:
  - apiGroups: [""]
    resources: ["services", "configmaps", "secrets"]
    verbs: ["*"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["*"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: provider-kubernetes-target-binding
  namespace: team-a-apps
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: provider-kubernetes-target-role
subjects:
  - kind: ServiceAccount
    name: provider-kubernetes-target
    namespace: crossplane-system
```

## 5. Create the kubeconfig Secret with the token injected

This is the kubeconfig that `provider-kubernetes` will use. It points to the in-cluster API server and uses the SA token.

Run this script to generate and apply it:

```bash
#!/bin/bash
TOKEN=$(kubectl get secret provider-kubernetes-target-token -n crossplane-system -o jsonpath='{.data.token}' | base64 -d)

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: target-cluster-kubeconfig
  namespace: crossplane-system
type: Opaque
stringData:
  kubeconfig: |
    apiVersion: v1
    kind: Config
    clusters:
    - name: in-cluster
      cluster:
        server: https://kubernetes.default.svc
        insecure-skip-tls-verify: true
    contexts:
    - name: in-cluster
      context:
        cluster: in-cluster
        user: provider-sa
    current-context: in-cluster
    users:
    - name: provider-sa
      user:
        token: $TOKEN
EOF
```

**Note**: `insecure-skip-tls-verify: true` is fine for a lab. For production, you'd embed the cluster's CA cert instead.

## 6. Create the ProviderConfig

This tells `provider-kubernetes` to use the kubeconfig Secret you just created.

```yaml
apiVersion: kubernetes.crossplane.io/v1alpha1
kind: ProviderConfig
metadata:
  name: target-cluster
spec:
  credentials:
    source: Secret
    secretRef:
      namespace: crossplane-system
      name: target-cluster-kubeconfig
      key: kubeconfig
```

## 7. Verify it works

Check that the ProviderConfig is healthy:

```bash
kubectl get providerconfig target-cluster
```

You should see it in a `READY` state (or at least not erroring).

Now apply the `App` claim from the previous example:

```yaml
apiVersion: example.org/v1alpha1
kind: App
metadata:
  name: web
  namespace: team-a
spec:
  compositionRef:
    name: xapps.example.org
  parameters:
    targetNamespace: team-a-apps
    image: nginx:1.27
    replicas: 2
    containerPort: 8080
```

Then check that the Deployment and Service appear in `team-a-apps`:

```bash
kubectl -n team-a-apps get deployment,service
```

You should see:

```
NAME                        READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/web-deploy  2/2     2            2           30s

NAME              TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
service/web-svc   ClusterIP   10.96.123.456   <none>        80/TCP    30s
```

## Alternative: InjectedIdentity (simpler but less realistic)

If you want to skip the SA/token/kubeconfig dance entirely for a quick lab test, you can use `InjectedIdentity`, which makes the provider use its own pod service account.

```yaml
apiVersion: kubernetes.crossplane.io/v1alpha1
kind: ProviderConfig
metadata:
  name: target-cluster
spec:
  credentials:
    source: InjectedIdentity
```

But you'd still need to grant the provider's SA (usually `provider-kubernetes` in `crossplane-system`) the right permissions via a ClusterRole/ClusterRoleBinding or Role/RoleBinding. This is simpler to set up but less realistic for production, where you'd want scoped-down credentials.

For a lab that teaches the right mental model, I'd stick with the dedicated SA approach above.
